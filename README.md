## 核心思路

### 1. 先定接口，再写实现

两个头文件是"契约"：函数名、参数、返回值、边界行为全部写死。两套实现必须满足同一份契约，
测试代码只依赖契约。这是 C 里模拟"面向接口编程"的土办法，收益是：**测试只写一遍**。

用宏切换实现（`tests/test_list.c` 开头）：

```c
#ifdef USE_SEQLIST
#define list_insert seq_insert
#define LIST_T      SeqList
#else
#define list_insert llist_insert
#define LIST_T      LinkedTaskList
#endif
```

编译时 `-DUSE_SEQLIST` / `-DUSE_LINKEDLIST` 各编一次，就是两个独立的测试二进制。

### 2. 顺序表：三个字段，一次 memmove

```c
struct SeqList {
    Task *data;   // 连续内存
    int   size;   // 用了多少
    int   cap;    // 申请了多少
};
```

- **扩容 1.5 倍**，不是每次 `+1`。每次 `+1` 的话 n 次尾插要搬 `1+2+...+n` 次，退化成 `O(n²)`；
  1.5 倍或 2 倍增长能把**均摊**代价压到 `O(1)`。这就是"均摊分析"在工程里的样子。
- **中间插入就是一次 `memmove`**：把 `[pos, size)` 整体后移一格。要搬多少个元素，就是它的代价，
  所以是 `O(n)`。尾插时 memmove 长度为 0，什么也不搬，所以是 `O(1)`。
- **删除只是 `size--`**，内存不还。这就是"顺序表删除不释放空间"的含义。
- `memmove` 不能换成 `memcpy`：源和目标区间重叠时 `memcpy` 行为未定义。

### 3. 单链表：三条不变量撑起全部正确性

```
       head(哨兵)                            tail
         |                                    |
         v                                    v
      [ 哨兵 ] --> [ 数据 ] --> [ 数据 ] --> [ 数据 ] --> NULL
```

**三条不变量**，每个函数返回前都在脑子里过一遍：

1. `head->next ... tail` 就是全部数据结点，共 `size` 个
2. `tail->next == NULL`
3. 空表时 `head->next == NULL`、`tail == head`、`size == 0`

**为什么要哨兵（头结点）？** 如果 `head` 直接指向第一个数据结点，那么"在表头插入"要改 `head` 本身，
"在别处插入"改的是某个结点的 `next` —— 两种写法、两套边界判断。有了哨兵，**所有插入都变成"改某个结点的 next"**，
代码少一半 if。代价只有一个结点。

**为什么要 tail？** 尾插不用从头走到尾。但注意：**光有这个字段没用，得真的用它**（见下面的实测教训）。

### 4. 两处指针顺序，错了就丢链

**插入**（`llist_insert`）：

```c
n->next = prev->next;   /* 1. 新结点先接上后半段 */
prev->next = n;         /* 2. 前驱再指向新结点   */
```

顺序反了就先把 `prev->next` 改掉了，后半段的入口丢失，整条链从 `pos` 开始泄漏。
**记忆法：先接后断。**

**删除**（`llist_remove`）：

```c
prev->next = victim->next;   /* 摘链 */
if (l->tail == victim) l->tail = prev;   /* 删的是尾巴，tail 要退回前驱 */
free(victim);                /* 摘下来之后再释放 */
```

`free` 之后不能再碰 `victim->next` —— 所以要先摘链再释放。忘了更新 `tail`，它会指向已释放的内存，
下一次尾插就是写坏内存。

### 5. 逆序：三指针

```c
cur = l->head->next;
l->tail = cur;              /* 原来的第一个结点会变成最后一个 */
while (cur != NULL) {
    next = cur->next;       /* 1. 先存住后半段 */
    cur->next = prev;       /* 2. 掉头 */
    prev = cur;             /* 3. 齐步走 */
    cur = next;
}
l->head->next = prev;       /* 哨兵接回新的第一个结点 */
```

全程没有 `malloc`、没有换结点，只把每条 `next` 反过来 —— 所以是 `O(n)` 时间、`O(1)` 额外空间。

### 6. 归并：链表比数组干净

数组归并要么额外开一个 `O(m+n)` 的数组，要么就地归并搬得很难受。
链表归并只需要**按顺序把值抄进 dst**：

```c
while (pa && pb) {
    if (task_compare(&pa->task, &pb->task) <= 0) { push_back(dst, pa->task); pa = pa->next; }
    else                                         { push_back(dst, pb->task); pb = pb->next; }
}
```

两边各走一遍，`O(m+n)`。这是链表在"归并/拆分"类问题上的真正优势，也是归并排序用链表实现更自然的原因。

## 测试是怎么设计的

11 个用例，覆盖的是**契约**而不是实现细节：

| # | 用例 | 抓什么 bug |
|---|---|---|
| 1 | 空表：size / at / remove / reverse | 空表上的边界判断 |
| 2 | 尾插 + 越界访问 | `at` 的上下界 |
| 3 | 头插 / 中间 / 尾插 | `pos == 0` 和 `pos == size` 两个特殊位置 |
| 4 | 非法位置插入 | 拒绝后表**必须原样不动**，不能插了一半 |
| 5 | 中间 / 尾部 / 头部删除 | 删尾时 `tail` 有没有退回 |
| 6 | 非法位置删除 | 同上 |
| 7 | 查找：多个命中 / 无命中 / 缓冲区截断 / 只统计 | 返回值语义（命中总数 ≠ 写入个数） |
| 8 | 逆序：空 / 单个 / 偶数 / 奇数 | 三指针的两端 |
| 9 | 归并：dst 有旧数据 / 两边空 / 一边空 / 优先级相同 | 归并的四个退化场景 |
| 10 | 存盘读盘往返 + 读不存在的文件 | 序列化格式、失败返回 |
| 11 | 2000 条压测 + 删空后再插入 | `tail` 在删空后有没有回到哨兵 |

几个设计要点，值得抄走：

- **断言失败不中断**（不像 `assert`），一次运行看到所有问题，而不是改一个跑一次。
- **先判 NULL 再解引用**：`const Task *t = list_at(l, i); CHECK(t != NULL); if (!t) return;`
  这样实现有 bug 时报 FAIL，而不是段错误 —— 崩掉的测试比失败的测试难查十倍。
- **两种实现跑同一份测试**：如果两边报**同样的**错，说明是测试写错了；只报一边，才是实现的问题。
  （开发这个项目时就靠这招抓到两个自己写错的期望值。）
- **交叉测试**（`test_cross.c`）：`seq_save` 的文件必须能被 `llist_load` 读进来，反之亦然。

## 基准测试：实测数据会打脸教科书

本机实测（Windows / MSVC 14.51 `/O2`，**数字随机器变化，看比例不看绝对值**）：

**N = 20 000 元素，随机类操作各 2 000 次**

| 实现 | push_back | 随机位置 insert | 随机 at() | 头部 remove(0) |
|---|---:|---:|---:|---:|
| SeqList | 0.75 ms | **10.9 ms** | **0.03 ms** | 30.1 ms |
| LinkedTaskList | 1.3 ms | 22.5 ms | 51.6 ms | **0.04 ms** |

**N = 100 000 元素，随机类操作各 10 000 次**

| 实现 | push_back | 随机位置 insert | 随机 at() | 头部 remove(0) |
|---|---:|---:|---:|---:|
| SeqList | **4.2 ms** | **276 ms** | **0.09 ms** | 2421 ms |
| LinkedTaskList | 4.9 ms | 1471 ms | 2869 ms | **1.2 ms** |

### 三个必须自己能解释的现象

1. **随机 `at()`：差 3 万倍。** 数组一次乘加算出地址；链表要跳 5 万次指针，每次都可能是缓存未命中。
2. **头部删除：差 2000 倍。** 数组每次要搬 10 万个元素（`O(n)`）；链表只改两个指针（`O(1)`）。
   这是链表唯一"压倒性获胜"的场景 —— 也正是**队列**用链表实现的原因。
3. **随机位置插入：数组反而快 5 倍。** ← 这条和教科书的"链表插入快"直接矛盾。

第 3 条要能讲清楚：教科书说的"链表插入 O(1)"，**指的是"已经拿到前驱指针"之后的指针改写**。
而按**下标**插入，你必须先 `O(n)` 走到那个位置 —— 链表走位是随机访存（每次几乎都缓存未命中），
数组 `memmove` 是顺序访存（还能被 SIMD 向量化）。**同样是 O(n)，常数能差一个数量级。**
所以"复杂度相同"从来不等于"一样快"。

> **一个真实教训**：第一版 `llist_push_back` 我偷懒写成 `return llist_insert(l, l->size, t)`，
> 而 `llist_insert` 要先 `prev_at(pos)` 找前驱 —— `pos == size` 时那是"从头走完整条链"的 `O(n)`。
> 于是 2 万次尾插跑了 **582 ms**（数组 0.75 ms），整体退化成 `O(n²)`。
> 明明 `tail` 就指着尾巴，却没用上。**"有 tail 指针的尾插才是 O(1)"，这句话的重点是"用上"。**

## 接下来改什么（按难度递增）

1. **加 `ls_foreach` 回调**：`void (*visit)(const Task *, void *)`，体会 C 里怎么传"行为"。
2. **双向链表**：加 `prev` 指针，实现 `O(1)` 删除"当前结点"，再加一个迭代器。
3. **迭代器抽象**：让 `save` 不再依赖 `at()`，否则链表存盘是 `O(n²)`（现在就是，去算算）。
4. **LRU 缓存**：哈希表 + 双向链表，线性表在工业界最经典的用法。
5. **跳表**：给链表加"分层索引"，把查找从 `O(n)` 压到 `O(log n)` —— 你会真正理解"链表缺的是索引"。

## 常见坑清单

- `free` 之后还用 `p->next` → 先存 `next`，再 `free`
- `realloc` 之后还用旧指针 → 必须 `p = realloc(...)`
- 删掉最后一个元素后 `tail` 没退回哨兵 → 下次尾插写坏内存（用例 11 专门抓这个）
- 顺序表扩容忘了用返回值，或扩容后 `cap` 没更新
- 非法位置插入"插了一半"才返回错误 → 先校验，再分配，最后改指针
- 泄漏：`destroy` 要逐个 `free` 数据结点，再 `free` 哨兵，最后 `free` 表头
